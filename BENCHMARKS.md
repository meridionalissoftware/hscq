# hsc benchmarks — compression ratio, distortion, and open-weight vectors

Generated by `python3 scripts/ratio_report.py > BENCHMARKS.md`. The corpus is not in the
repo; build it with `python3 scripts/corpus.py fetch && python3 scripts/corpus.py models`.

## How to read every table here

hsc is **fixed-rate**. For a given `(mode, dim, level, gain_bits)` the compressed size is
identical for `/dev/urandom` and for JSON — that is the library's guarantee, and it means
**the ratio column carries no information about the data**. What a corpus decides is the
*distortion* at that rate. So:

* the fixed-rate grid varies `rmse`/`psnr` down a corpus and holds `ratio` constant;
* the **quality-matched** table fixes a distortion target and searches for the cheapest
  configuration that meets it — that ratio *is* data-dependent, and it is the only number
  here that answers "what does hsc get on my data?";
* a `dg=1` row is **degenerate**: `shape_bits == 0`, the recursion collapsed to `M == 1`,
  the shape field has zero width and the record carries the gain alone. Those rows show
  enormous ratios and are not compression. They are excluded from every search.

Two rate conventions appear below and they are not the same number. hsc rows in the
preset chart and the fixed-rate grid print the **payload** rate — block records only —
which is what the `quant.hpp` preset constants state and what `tests/quant.cpp` pins
against `hsc::rate()`. The frame is a flat 48 bytes per stream (40 header + 8 trailer),
so `qplan::bits_per_weight`, which counts it along with the final pad bits, is always
slightly larger. The measured `ratio` column in the same rows is FRAMED — whole stream
over input, 48 B included — so `ratio` and `8 / bits-per-byte` differ by the frame share.
Coder rows count every byte the coder emits.

## Presets vs coders — the one chart

`src/hsc/quant.hpp` declares a seven-entry preset ladder — `q_min` … `q_finest` — and
those are the library's own default answers to "how should I store this?". This is the
only place in the report that measures them, and it puts them in the same table as the
alternatives: the four lossless coders, and the int-N a weight quantizer would ship.

Read the `lossy` column first. zstd/xz/bzip2/gzip reproduce the input exactly and their
ratio is whatever the data allows — unknowable until they have run. int-N and hsc are
lossy; hsc's ratio is a constant of the configuration, guaranteed on any input at all.
The two blocks use different PSNR references (peak-magnitude for f32 tensors, 8-bit full
scale for bytes) and must not be read as one table.

## hsc vs lossless coders, same 512 KiB prefix

**This is context, not a contest.** These coders are lossless; hsc is lossy. The point of
the table is the shape of the two columns, not a winner: an entropy coder's ratio swings
from 1.00x (incompressible) to hundreds (long runs) and it cannot promise anything in
advance, while hsc's is a constant it guarantees on any input at all.

| corpus | what it is | n (B) | zstd-19 | xz-9 | bzip2-9 | gzip-9 |
|---|---|---:|---:|---:|---:|---:|
| `urandom` | /dev/urandom | 524,288 | 1.00x | 1.00x | 0.99x | 1.00x |
| `random` | /dev/random (same CSPRNG) | 524,288 | 1.00x | 1.00x | 0.99x | 1.00x |

For contrast, hsc's **payload-rate** ratio is set by the configuration alone and is the
same for every one of those inputs: 2.13x at dim8 L6, 2.84x at dim16 L6, 5.57x at dim64 L6,
22.26x at dim64 L2 — with the distortion cost measured below. (The measured grid rows
print the framed ratio, a hair lower: the 48-byte frame over a 512 KiB prefix.)

## The compression-ratio model

Rate is **exact** — a closed form validated cell by cell against real streams. Distortion
is **empirical**, `rmse ~= min(kappa(dim) * d * sigma, sqrt(2) * sigma)`, with `sigma` the
RMS of the centered bytes. The fitted `kappa(dim)` tracks `0.29*sqrt(dim)`, and the
residuals are reported split by validity domain rather than averaged into one flattering
number.
